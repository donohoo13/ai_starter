## PR description draft

### Summary

The template's spec-driven development chain went from an approved spec straight to a technical plan, and its standards hard-coded design values such as touch-target size, reading width and allowed CSS units.
No phase requested, waited for or recorded a UI design, so implementer agents decided layout and flow mid-build and the hard-coded values overrode each project's own design system.
Claude Design now runs as artifacts in Claude and in Claude Code, so a project can get mockups designed against its own design system before any plan exists.
Without a gate for that work, approved designs never reached the plan, design changes that implied new behavior bypassed the spec, and nobody saw a layout until QA.
This change adds an optional Design phase that writes a Claude Design prompt from the approved spec and records the design the user approves, makes DESIGN.md the authority the standards defer to, and rebuilds design-init around a template it carries.
Design approval is a gate with its own state in the SDD helper, and every design value lives in one file that each project decides.
A UI spec now passes through an approved, committed design before planning, render checks run only on surfaces the user picks, and the design system in Claude is rebuilt from the repository.

### What changed

- A Design phase between Outline and Plan: `design.md` as a fifth artifact, `set-status design requested|skipped`, `approve design`, status reporting `2. Design` while a design is requested, changed or stale, the spec's `## UI surfaces` section with linted `UI-` IDs, and phases and sections renumbered throughout.
- The `sdd-design` skill with its prompt and record references: it writes the prompt, reads a returned Design artifact into a committed snapshot under the spec folder's `design/` directory, puts each miss and gap to the user, re-checks against a revised spec, and approves on the user's word; it never invokes `/design` or publishes an artifact.
- The approval hash for design, plan and tasks covers the body plus `based_on`, and a design's recorded `version`, so a re-approval against a changed upstream always stales what follows; approvals recorded under the earlier body-only hash stay current.
- `sdd-implement` asks which UI surfaces get a render check at the first start or a resume, records the answer in `tasks.md`'s `render_check` and `render_check_asked` frontmatter keys, and dispatches `render-checker` once before QA with failures and Not reached entries in the QA script; `render-checker` judges against the WCAG 2.2 AA floors, DESIGN.md and the design snapshot, with `/render-check` and `sdd-implement` as its two dispatchers.
- `ux-standards.md` splits into WCAG 2.2 AA floors cited by success criterion and labeled starting values; `frontend-styling.md` states units as a principle and bars Claude Design runtime markup from shipped UI; `html-tables.md` keeps markup and layout as requirements and labels styling as starting values; the implementer self-check and `standards-reviewer` judge surfaces against DESIGN.md with the starting values as the fallback while it is absent, unfilled or silent.
- The root `DESIGN.md` scaffold is deleted; `design-init` writes it from its own template with decision tables for the deferred values and a Claude Design System section, briefs the structure, decides identity in five rounds, refuses values below a floor, finishes on a clean `designmd lint`, and offers to build or re-sync the project's Design System in Claude; `curate-context` applies the same floor refusal and re-sync offer.
- `CLAUDE.md`, the root README, the skills README and the SDD README describe the new chain; `gut-check.md` holds the fresh-session prompts for every changed skill; `.prettierignore` excludes design snapshots so the pre-commit hook cannot reformat them; `CHANGELOG.md` records the change with adaptation notes.

### Decisions and follow-ups

- Approvals recorded under the earlier body-only hash still count as current, so no in-flight artifact here or in a child project routes back to Plan; a hand edit to `based_on` on such an artifact stays undetected until its next re-approval.
- A skipped design's coverage is judged by UI ID, as FR-011 specifies; a surface redefined under the same ID keeps the skip, which a later spec may revisit by hashing the surface lines.
- `render_check_asked` is a second frontmatter key because a `none` or declined answer leaves no record of what was asked.
- The DESIGN.md template's Claude Design System link ships as "not built yet" rather than a bracket placeholder, so a finished file reads as filled.
- Reading width stays at `70ch`, the standard's value; the template's old `65ch` was aligned to it.
- The changelog entry reverses the spec's non-goal on the user's decision after the build.
- The gut-check prompts for record, re-check, render check and `design-init` have no recorded run; the user chose not to run them now.
- Follow-up: `sdd-review`'s conformance review hands its subagent the spec, plan and tasks only, so an approved `design.md`'s Accepted misses and Not built list are checked only by the implementer self-check and an opted-in render check; a later spec should have Validate read `design.md`.
