# Claude design integration plan

## Approach

The design phase joins the SDD helper's artifact chain as `design.md`, with the plan's upstream switching from the spec to the design whenever a design is approved, so staleness keeps flowing through one `based_on` per artifact.
The spec template gains a UI surfaces section of `UI-001`-style IDs that the helper compares against a skip's covered surfaces.
One state-driven `sdd-design` skill writes the prompt, records skips and cancels, and turns a returned Design artifact link into a committed snapshot under the spec's `design/` folder, with the prompt template and the record procedure in its `references/`.
`sdd-implement` asks for render-check surfaces at its start, records the answer in `tasks.md`'s frontmatter, and dispatches `render-checker` once before QA.
The three standards are rewritten to WCAG 2.2 AA floors plus starting values that DESIGN.md overrides, and the judges read DESIGN.md.
`design-init` is rewritten around its committed template, and builds or re-syncs the Design System artifact in Claude by following that artifact type's own instructions at run time plus one mapping reference that `curate-context` shares.
Everything ships in one pull request, built slice by slice in the spec's order.

## Technical context

- Stack and versions: the SDD helper is a Python 3 standard-library script (local Python 3.14.7) tested with `unittest`; the script batteries run on Node 24.18.1 (`.nvmrc`) through pnpm; `@google/design.md` 0.4.0 provides `pnpm exec designmd lint|diff|export`; Prettier ^3.8.4 formats Markdown.
- Dependencies: no new package; the Artifact tool and the Design and Design System artifact types come from Claude Code in a claude.ai-authenticated session; `/design` needs Claude Code v2.1.265 or later (installed: 2.1.319).
- Platform limits: the Artifact tool is absent in sessions authenticated by API key, Bedrock or Vertex; a read of an artifact the user does not own returns a summary instead of files; Claude Design has no version history; `designmd` types front-matter dimensions only in `px`, `em` or `rem`, so `ch` and `ms` values live in section tables.

## Architecture

- **SDD document** (`.claude/sdd/spec-driven-development.md`): the source of truth for the new phase.
  A new section 8, Phase 2: Design (`sdd-design`), describes the steps, the prompt, the snapshot, misses and gaps, and the gate; sections 8 to 15 become 9 to 16.
  Section 4's workflow, state and phase tables gain the Design row and the renumbered labels; section 5 lists `design.md` and `design/`; section 7 adds the UI surfaces section and the finish offer; the Plan section loads an approved design; the Implement section adds the render-check offer, the pre-QA render pass, and `tasks.md`'s `render_check` key in the orchestrator's write list.
  Appendix A gains the UI surfaces section, a new Appendix B holds the design record template, and the plan, tasks and review templates move to C, D and E.
- **SDD helper** (`.claude/sdd/bin/sdd`): owns state.
  `design` joins `ARTIFACTS` after `spec`; a function returns the plan's upstream (the design when `design.md` is `approved`, otherwise the spec), used by `chain_states`, `upstream_check`, `lint_based_on` and `approve`.
  `derive_phase` reports `2. Design` for a `requested` design, an approved design that is changed or stale, or a skip that misses a spec UI ID, and the renumbered labels otherwise.
  `lint` gains a design linter and UI-ID checks in the spec linter; `approve` accepts `design`; `set-status` gains `design requested` and `design skipped`, creating `design.md` from its template when absent; `check-refs` scans `sdd-design`.
- **`sdd-design` skill** (new, `.claude/skills/sdd-design/`): reads `design.md`'s state and does one of request, skip, cancel, record, re-check or approve, every write gated on the user's word and staged by explicit path.
  `references/design-prompt.md` holds the prompt template; `references/record-design.md` holds the snapshot, misses-and-gaps and approval procedure.
- **Chain skills**: `sdd-outline` writes the UI surfaces section and offers design at its finish; `sdd-plan` asks or loads the design; `sdd-task` and `sdd-review` take the renumbered labels and sections; `sdd-implement` adds the render-check offer, its record, the pre-QA dispatch and the failure hand-off.
- **Render checking**: `render-check`'s bar step and `render-checker`'s bar and target-size measure change; the process-suite battery allows `sdd-implement` as a second dispatcher.
- **Standards and judges**: `ux-standards.md`, `frontend-styling.md` and `html-tables.md` split floors from starting values; `implementer` and `standards-reviewer` read DESIGN.md on surface diffs, and `standards-reviewer` checks for Claude Design runtime markup.
- **`design-init`** (rewritten): the interview over `references/design-template.md` (rewritten from the root scaffold), `references/brand-research.md` (kept), and `references/claude-design-system.md` (new mapping onto the Design System artifact type).
  `curate-context` gains the below-floor refusal, the absent-DESIGN.md clause and the re-sync offer pointing at the same mapping file.
- **Root files**: `DESIGN.md` is deleted; `CLAUDE.md`, `README.md`, `.claude/skills/README.md` and `.claude/sdd/README.md` describe the new behavior.

## Data model

- **`design.md`** (new, `docs/sdd/{slug}/design.md`), frontmatter:
  - `title`, `slug`, `updated`.
  - `status`: `requested`, `approved` or `skipped`.
  - `based_on`: the spec's `approved_hash` at request, skip or approval; `approved_hash`: the body hash at approval.
  - `decided_by`: git `user.name` for a skip or cancel; `surfaces`: the comma-separated UI IDs a skip covers.
  - `link`, `version` (the artifact version id read), `read` (date), `design_system` (the link the canvas used, or `none`).
- **`design.md` body**: `## Prompt` (the prompt text, or "None" for a skip), `## Artboards` (one line per artboard: file, UI ID, state, requirement IDs, PNG if any), `## Accepted misses`, `## Not built`, `## Skip reason`, each "None" when empty; the hash covers the body.
- **Snapshot** (`docs/sdd/{slug}/design/`): `canvas.json`, one `*.dc.html` per artboard, `tokens.json` when the canvas used a design system, and any `*.png` the user adds named after an artboard's file stem; a re-read deletes the earlier `*.dc.html` files first.
- **Spec UI surfaces** (`## UI surfaces` in the spec): one line per surface, `- UI-001: Settings screen (new)` or `(edited)`; IDs are permanent like requirement IDs, and the spec linter rejects a malformed or duplicate ID.
- **`tasks.md` frontmatter**: `render_check:` holding the approved UI IDs, comma-separated, or `none`; absent means not yet asked; frontmatter is outside the content hash.
- **DESIGN.md**: a `## Claude Design System` section holding one `- Link:` line, present only after a successful build; deferred values sit in section tables (Layout's accessibility and units tables, Typography's measure, Motion's table, Components' Data table).
- **Migrations**: none; specs without `design.md` or a UI surfaces section keep working, and `docs/sdd/implement-orchestrator/` needs no change.

## Interfaces and contracts

- **Helper CLI**:
  - `sdd set-status {slug} design requested` creates `design.md` from its template when absent and records `requested` and `based_on`.
  - `sdd set-status {slug} design skipped` records `skipped`, `based_on`, `decided_by`, `surfaces` (the spec's current UI IDs) and `updated`.
  - `sdd approve {slug} design` refuses on lint errors or a missing `link`, `version` or `read`, then records `approved`, `approved_hash` and `based_on`.
  - `sdd lint {slug} design`; `sdd status` prints a `design` row, and its JSON adds `artifacts.design`.
- **Phase labels**: `1. Outline`, `2. Design`, `3. Plan`, `4. Tasks`, `5. Implement`, `6. Validate`, `Done`.
- **Design prompt** (`sdd-design/references/design-prompt.md`): goal and audience; surfaces with UI ID, states and requirement IDs; devices and widths; things not to design; the design system (link, DESIGN.md excerpt, or no decisions yet); WCAG 2.2 AA floors and DESIGN.md's or the starting values; the copy rule; the process (two or three directions on the primary screen, then one artboard per screen and state titled like `UI-001 Settings / empty`); and a closing line asking the user to bring the approved design's link back.
  No repository path, shell command, SDD tool name or em-dash.
- **Design record** (input): a claude.ai artifact link the user owns; read with the Artifact tool's `read` and `paths` for `project/canvas.json`, each `project/*.dc.html` from a `files` listing, and `project/ds/*/tokens.json`.
- **`render-checker` brief**: URL; surfaces with UI ID, name and states; shipped themes; the bar (WCAG 2.2 AA floors, DESIGN.md or the starting values, and per designed surface its artboard files and `Not built` list); the report format is unchanged.
- **Design System mapping** (`design-init/references/claude-design-system.md`): DESIGN.md colors and their `-dark` siblings become `tokens.json` color tokens with per-theme values; typography, spacing and rounded map to the type, spacing and radius families; the Overview, Voice & Copy and Do's and Don'ts prose becomes the README brand book; each component's prose becomes `components/{Name}/README.md`; the build itself follows the Design System type's own `SKILL.md`, read through the Artifact tool at run time.

## Seams and test strategy

The discovery found two automated tiers and one manual one.
Commands: one helper test file is `python3 -m unittest discover -s .claude/sdd/tests -p test_design.py`; one battery is `pnpm exec node scripts/test/process-suite.battery.mjs`; the full suite is `pnpm test:scripts`; formatting is `pnpm format:check`.
Helper tests drive the CLI in process through `helpers.py` against a throwaway git repo and a temporary `SDD_HOME`, doubling nothing; batteries read the real suite files; skills and documents have no executable seam, so they are checked against their acceptance criteria by reading, by `check-refs` and the token measure, and by the gut-check prompts the user runs in a fresh session and records in `docs/sdd/claude-design-integration/gut-check.md`.

### P1: Approve a design before planning

- Seam: the helper CLI through `helpers.py`'s in-process runner, the repo's established seam for the helper; skill and document text for the rest.
- Test types: `unittest` helper tests; `templates sync --check` and `check-refs` through the helper battery; text checks and gut-check runs.
- Acceptance criteria to tests:
  - FR-001 → `test_templates.py`: sync writes five templates including `design.md`; `check-refs` scans `sdd-design`.
  - FR-002, FR-003, FR-005, FR-006, FR-011 → `test_design.py` and the relabeled `test_status.py`: each status, each phase label, plan staleness after a design approval, a skip re-offered for a new UI ID.
  - FR-007 → `test_lint_spec.py`: a malformed or duplicate UI ID is an error; the template carries the section.
  - FR-004, FR-008 to FR-010, FR-012 to FR-027, INV-001, INV-002, INV-004 → reading each skill against its criterion, and the P1 gut-check run with one of the user's own Design artifacts.

### P2: Opt into render checks when the build starts

- Seam: the process-suite battery for the dispatcher rule; skill and agent text for the rest.
- Test types: node battery; text checks; gut-check run in a project that ships UI.
- Acceptance criteria to tests:
  - FR-035 → the dispatcher check fails once `sdd-implement` names `render-checker`, then passes with the allowlist updated; a scratch skill naming `render-checker` still fails it, recorded in the task's Evidence and removed.
  - FR-028 to FR-034, NFR-002 → reading `sdd-implement`, `render-check` and `render-checker` against their criteria, and the P2 gut-check run.

### P3: Design values each project decides

- Seam: the standards and agent files themselves.
- Test types: text checks; the P3 gut-check run of `standards-reviewer` on a surface diff with and without DESIGN.md.
- Acceptance criteria to tests: FR-036, FR-038 to FR-042, INV-003, INV-005 → each file read against its criterion.

### P4: Generate DESIGN.md from the skill's own template

- Seam: `design-init`'s files and `pnpm exec designmd lint` on the run's output.
- Test types: text checks; `designmd lint`; the P4 gut-check run on a fixture overview and a reference DESIGN.md the user supplies.
- Acceptance criteria to tests: FR-037, FR-043 to FR-052, INV-006, INV-007 → each file read against its criterion; the gut-check output passes lint and the residue check of FR-048.

### Cross-cutting

- FR-053, NFR-001, NFR-003 → reading the four overview files; the token measure per changed skill body; `pnpm format:check` and `pnpm test:scripts` at every slice close.

## Alternatives considered

- Design outside the chain with two hashes on the plan: rejected by the user; every staleness rule would grow a second hash.
- UI surfaces by name only: rejected by the user; a rename would read as a new surface and re-offer design.
- Two design skills (request and record): rejected by the user; two names for one phase.
- The full Design System build procedure in our own reference: rejected by the user; it drifts whenever Anthropic changes the type.
- A separate `render-check.md` record: rejected by the user; a fourth file for the orchestrator to write and a resume to find.
- Battery content checks for the template, the standards and runtime markup: rejected by the user; prose greps break on rewording and ship into every child project.
- Appending the design template as Appendix E: rejected because the phases are renumbered anyway, so the appendices follow phase order.
- `/design-sync` for the Design System artifact: a spec non-goal; it targets the standalone site.

## Trade-offs and risks

- Renumbering touches every chain skill, both READMEs and the helper tests: `check-refs` and the relabeled status tests catch a missed reference.
- Skill behavior cannot run in CI: each changed skill gets gut-check prompts, and the user records the runs before `sdd-review`.
- The Artifact tool's behavior (A-001, A-002) may change: the edge cases stop without a snapshot instead of guessing, and the mapping reference is the only part that restates the type.
- Projects created after this ship no DESIGN.md until `design-init` runs: every reader falls back to the starting values, which FR-043 states in each file.
- `sdd-implement`'s body grows past 1,837 words: the render-check steps stay short, and NFR-001's measure moves detail into a reference if the body nears 5000 tokens.
- The unreleased v0.3.0 changelog entry will contradict the shipped behavior: accepted by the user pending the changelog restart.

## Rollout

1. One pull request from `feature/claude-design-integration`, built and committed slice by slice in the order P1, P2, P3, P4, each slice leaving `pnpm format:check` and `pnpm test:scripts` green. Rollback: revert the pull request; no data or migration is involved.

## Research notes
