# SDD (Spec Driven Development) Template

_The high level ask or task at hand to be completed_

## Product Requirements

_The what and the why of what's being built when applicable_

### Problem

_The problem at hand we are attempting to solve_

### User Stories

_The persona + verb stories that our task is going to address_

## Design Requirements

_The visual representation that must be followed for the task when working with front end environments_

### Controls

_The physical elements that need to be created or augmented from a user perspective_

### Layout and Hierarchy

_The visual structure that must be respected or implemented including typography and display surfaces like dialogs, chips, tooltips etc._

## Engineering Requirements

_The engineering portion that mostly looks and feels like a TRD (Technical Requirement Document) but molded into the new form that does not disagree with the Product Vision and Design elements when applicable but instead works with them_

### Slices

_The actionable vertical slices or pieces of engineering work that need to get done in order to get a result that satisfies the original task_

### Architecture

_The frameworks, patterns, system design, or any other high level concepts or tools that are required or desired for the implementation_

## Evidence

_The research if any backing the decisions that are made for implementation e.g. using a sheet instead of dual dialogs for better user experience when displaying more contextual information or choosing one framework or package over another for specific for it's pricing structure_

## References

_The files in the codebase that would drive the best results if pulled into the implementators context window early_

### Sources

_The contextual research that drive the evidence_

## Out of Scope

_non-goals, named so the task does not expand silently_

## Rejections

_The options that were discussed thoroughly but rejected_
